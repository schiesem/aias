### CQ 01: Which communications exist, and which systems do they connect?

Baseline question of the pattern, ISO/IEC 7498-1, 5.1.3 c). Participants are collected per communication, so a communication appears once.

SELECT ?communication (GROUP_CONCAT(DISTINCT ?systemName; separator=", ") AS ?systems) WHERE {
  ?communication iso7498:connects ?system .
  BIND(REPLACE(STR(?system), ".*#", "") AS ?systemName)
} GROUP BY ?communication ORDER BY ?communication
```

### CQ 02: Which communications are connection-mode, which connectionless?

ISO/IEC 7498-1, 5.3 and 5.8.4. The two are disjoint, which the negative models check, so a communication carries at most one of them.

**Query** `tests/queries/cq02_transmission_mode.rq`

```sparql
PREFIX iso7498: <https://w3id.org/aias/odp/iso7498#>
PREFIX inst: <https://w3id.org/aias/odp/iso7498/instances#>
SELECT ?communication ?mode WHERE {
  { ?communication a iso7498:ConnectionModeAssociation .
    BIND("connection-mode" AS ?mode) }
  UNION
  { ?communication a iso7498:ConnectionlessModeAssociation .
    BIND("connectionless-mode" AS ?mode) }
} ORDER BY ?communication
```

**Results**

| Case | communication | mode |
|---|---|---|
| tc1_communication | CommunicationAB | connection-mode |
| tc2_layered | CommunicationAB | connection-mode |
| tc3_connectionless | CommunicationAB | connectionless-mode |
| tc4_multiendpoint | BusSegment | connection-mode |

**Interpretation.** The mode, told apart by the class. Cases 1, 2 and 4 are connection-mode, case 3
connectionless.

Clause 5.8.4 makes this a property of the communication rather than of the
data: a connectionless transmission carries no state between units, which is
why the two are separate classes rather than a flag.

### CQ 03: In which direction does a communication run?

ISO/IEC 7498-1, 6.5.1.1 calls the ultimate source or destination of data an end system, and 5.3.1.14 to 5.3.1.16 name the three directions. Direction is stated twice over, on purpose. The source and target systems say who sends and who receives; hasDirection says whether both directions are possible at once or only in turn, which the systems alone cannot express.

**Query** `tests/queries/cq03_direction.rq`

```sparql
PREFIX iso7498: <https://w3id.org/aias/odp/iso7498#>
SELECT ?communication ?direction
       (GROUP_CONCAT(DISTINCT ?src; separator=", ") AS ?sources)
       (GROUP_CONCAT(DISTINCT ?tgt; separator=", ") AS ?targets) WHERE {
  ?communication iso7498:hasSourceSystem ?s ; iso7498:hasTargetSystem ?t .
  OPTIONAL { ?communication iso7498:hasDirection ?d .
             BIND(REPLACE(STR(?d), ".*#", "") AS ?direction) }
  BIND(REPLACE(STR(?s), ".*#", "") AS ?src)
  BIND(REPLACE(STR(?t), ".*#", "") AS ?tgt)
} GROUP BY ?communication ?direction ORDER BY ?communication
```

**Results**

| Case | communication | direction | sources | targets |
|---|---|---|---|---|
| tc1_communication | CommunicationAB | TwoWaySimultaneous | SystemA, SystemB | SystemA, SystemB |
| tc2_layered | CommunicationAB | TwoWayAlternate | SystemA | SystemB |
| tc3_connectionless | CommunicationAB | OneWay | SystemA | SystemB |
| tc4_multiendpoint | BusSegment | TwoWayAlternate | SystemA, SystemB, SystemC, SystemD | SystemA, SystemB, SystemC, SystemD |

**Interpretation.** The direction, one row per case. Cases 1 and 2 are two-way simultaneous, case 3
one-way.

That case 3 changes here as well is the point of it. The mode was the one thing
changed, and the direction followed: 6.4 has connectionless transmission convey
a unit from one entity to one or more others without a return path being part
of the arrangement. The model states the consequence rather than describing it.

`hasDirection` is functional, so a communication runs in one direction, which
negative model 02 tests.

### CQ 04: Which communications have more than two participants?

ISO/IEC 7498-1, 5.3.1.4 calls a connection with more than two connection endpoints a multi-endpoint connection, and 5.3.1.9 defines data transmission as conveying service data units from one entity to one or more entities. The pattern asserts no cardinality on connects for that reason, so one communication can carry a whole bus segment rather than one object per pair. The count reads connects, which generalises the source and target properties, so a participant is counted once however it is named.

**Query** `tests/queries/cq04_multi_endpoint.rq`

```sparql
PREFIX iso7498: <https://w3id.org/aias/odp/iso7498#>
SELECT ?communication (COUNT(DISTINCT ?system) AS ?participants)
       (IF(COUNT(DISTINCT ?system) > 2, "multi-endpoint", "two endpoints") AS ?kind)
WHERE {
  ?communication iso7498:connects ?system .
} GROUP BY ?communication ORDER BY DESC(?participants) ?communication
```

**Results**

| Case | communication | participants | kind |
|---|---|---|---|
| tc1_communication | CommunicationAB | 2 | two endpoints |
| tc2_layered | CommunicationAB | 2 | two endpoints |
| tc3_connectionless | CommunicationAB | 2 | two endpoints |
| tc4_multiendpoint | BusSegment | 4 | multi-endpoint |

**Interpretation.** The participant count. Cases 1 to 3 answer with two endpoints, case 4 with four
and the label multi-endpoint.

Clause 5.3.1.4 names a connection with more than two connection endpoints a
multi-endpoint connection, and the threshold is computed rather than asserted,
so a model states its participants and the kind follows.

### CQ 05: Which communications state no transmission mode?

The mode is optional in this pattern, since a model may not know it yet. The subClassOf* step is required: a communication is typed as one of the two modes, and the reasoner does not materialise the superclass as a further type, so matching "a iso7498:Association" alone would find nothing.

**Interpretation.** Empty in all four cases: every communication is typed as one mode or the other.

The question cannot be enforced. A communication of the general class is

reports a gap where one exists and SHACL is where it would become a rule.

### CQ 08: Which layers does a case occupy, and which stay empty?

The seven layers of clause 6 are supplied as named individuals, and a model fills as many of them as it needs. Test case 1 describes a communication without naming a layer at all, test case 2 refines the same communication down to the three lower ones. The catalogue is used as the yardstick here rather than as the answer. The question is which of the seven a case has anything to say about, so the answer moves with the case even though the layers do not. How a layer is occupied is reported rather than reduced to a yes. A case may name a technology for a layer and say nothing else about it, or it may open the layer up into subsystems and entities, and the two are different depths of description. Test case 1 names four technologies and reaches five layers that way without describing any of them; test case 2 refines three of them into an architecture. A-box check: catalogue as yardstick. The seven layers are supplied and the answer reports, per layer, whether the case occupies it. Without a case every layer reads as empty, which is the correct answer rather than a finding: the question is about the case, the rows are the scale it is measured on.

**Query** `tests/queries/cq08_layers_occupied.rq`

```sparql
PREFIX iso7498: <https://w3id.org/aias/odp/iso7498#>
SELECT ?layerNumber ?layer ?occupied
WHERE {
  ?l a iso7498:Layer ; iso7498:layerNumber ?layerNumber .
  BIND(EXISTS { ?s a iso7498:Subsystem ; iso7498:atLayer ?l }     AS ?refined)
  BIND(EXISTS { ?t iso7498:realisesLayer ?l }                     AS ?viaTechnology)
  BIND(EXISTS { ?c iso7498:usesLayer ?l }                         AS ?stated)
  BIND(EXISTS { ?u a iso7498:DataUnit ; iso7498:atLayer ?l }       AS ?viaDataUnit)
  BIND(IF(?refined, "refined into subsystems",
       IF(?stated || ?viaTechnology || ?viaDataUnit, "named only", "empty")) AS ?occupied)

```

### CQ 10: Which communications name no technology?

The counterpart of question 09. Clause 1.3 states that the reference model implies no particular implementation or technology, so a communication without one is described completely as far as the standard is concerned. Test cases 1, 3 and 4 answer here, and that is not a defect in them: they describe the architecture of a communication and leave open what carries it, which is exactly what the reference model is for. The question matters once the pattern is used for a plant. A communication with no technology cannot be checked against a cable, a bus or a bandwidth, so the answer is the list of what a deployment still has to decide.

### CQ 11: Which subsystems lie above and below a given one?

Clause 5.2 arranges the subsystems of an open system into layers, and the architecture rests on what is above and below rather than on absolute numbers: an entity uses the service of the layer below and provides one to the layer above. The question is therefore asked relative to a subsystem of the case rather than to a fixed layer. It reports the neighbours within one open system, since the relation only means something inside one stack. Test case 1 answers empty, having no subsystems. Test case 2 answers with the three lower layers of its two systems.

  ?otherSubsystem iso7498:atLayer/iso7498:layerNumber ?otherLayer .

The layer is reported alongside, since a service means something only in relation to where it sits: the same name at layer 3 and at layer 7 describes different work. Only test case 2 answers. ### CQ 15: Which protocols do the entities employ?

Clause 5.2.3 defines the protocol as the rules governing the exchange between peer entities. Where question 14 reports the vertical relation, this one reports what governs the horizontal one. Reported per protocol rather than per entity, so the entities sharing one appear together. Two peer entities employing the same protocol is the normal case and the reason the concept exists: 5.2.3 has peer entities communicate by a protocol they both follow.
