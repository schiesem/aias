### CQ 01: Which process operators does a process consist of, and what enters and leaves each?

The baseline question of the pattern, answered per process: which operators a process contains, and what enters and leaves each of them. Inputs and outputs are collected per operator rather than listed as separate columns of one row. Listing them separately would join the two sets into their cartesian product, which reads as a pairing of an individual input with an individual output, and VDI 3682 asserts no such pairing. Question 07 records that limit.

**Query** `tests/queries/cq01_process_operators.rq`

```sparql
PREFIX vdi3682: <https://w3id.org/aias/odp/vdi3682#>
SELECT ?process ?operator
       (GROUP_CONCAT(DISTINCT ?input;  separator=", ") AS ?inputs)
       (GROUP_CONCAT(DISTINCT ?output; separator=", ") AS ?outputs)
WHERE {
  ?process a vdi3682:Process ; vdi3682:consistsOf ?operator .
  ?operator a vdi3682:ProcessOperator .
  OPTIONAL { ?operator vdi3682:hasInput  ?input }
  OPTIONAL { ?operator vdi3682:hasOutput ?output }
} GROUP BY ?process ?operator ORDER BY ?process ?operator
```

### CQ 06: Which operators begin a chain, which end one, and which state no order?

The counterpart of question 05. That one reports the order, this one reports where it starts and stops, and where it was never stated. An operator without a predecessor begins a chain and one without a successor ends it. Both are ordinary, and each level of a decomposed process has one of each. An operator with neither states no order at all, and whether that is a gap depends on where it sits. A decomposed operator carries its order on the level below, as O1 of Figure 5 does: the coarse view shows one step, the refined view orders the two it consists of. An elementary operator with no order is the case worth finding, since nothing else states when it runs. The two are therefore reported apart. The role is computed rather than asserted, so a model states its order once and this answer follows from it.

**Query** `tests/queries/cq06_chain_ends.rq`

```sparql
PREFIX vdi3682: <https://w3id.org/aias/odp/vdi3682#>
SELECT DISTINCT ?operator ?role
WHERE {
  ?operator a vdi3682:ProcessOperator .
  OPTIONAL { ?operator vdi3682:hasPredecessor ?pred }
  OPTIONAL { ?operator vdi3682:hasSuccessor   ?succ }
  BIND(EXISTS { ?operator vdi3682:isComposedOf ?anySub } AS ?isDecomposed)
  BIND(IF(!BOUND(?pred) && !BOUND(?succ),
          IF(?isDecomposed, "no order, ordered one level down", "no order stated"),
       IF(!BOUND(?pred), "starts a chain",
       IF(!BOUND(?succ), "ends a chain", ""))) AS ?role)
  FILTER(?role != "")
} ORDER BY ?role ?operator
```

**Results**

| Case | operator | role |
|---|---|---|
| tc1_decomposition | O11 | starts a chain |
| tc1_decomposition | O12 | ends a chain |
| tc1_decomposition | O1 | no order, ordered one level down |
| tc2_parallel | O11a | starts a chain |
| tc2_parallel | O12a | ends a chain |
| tc2_parallel | O1a | no order, ordered one level down |
| tc2_parallel | O1b | no order stated |
| tc3_alternative | O11a | starts a chain |
| tc3_alternative | O12a | ends a chain |
| tc3_alternative | O1a | no order, ordered one level down |
| tc3_alternative | O1b | no order stated |

**Interpretation.** Where the order starts, stops, and was never stated. Two operators begin and
end the chain in every case, and the interesting rows are the remaining ones.

`O1` of case 1 carries no order and is decomposed: the coarse view shows one
step and the refined view orders the two it consists of, so the order sits one
level down. That is Figure 5 working as intended.

Cases 2 and 3 add a second unordered operator, `O1b`, and it is elementary.
Nothing states when it runs, and nothing has to: it is the parallel or
alternative branch, and its relation to the other branch is stated by the flow
rather than by a sequence. The two situations are reported apart for that
reason, since only one of them would be a gap in a different model.

### CQ 10: Which states depend on which others?

Part 1, 4.1.2 carries the dependency alongside the flow, and the two say different things. A flow states that something passes from one element to another. A dependency states that one state is bound to another without anything passing between them, as a piece of information is bound to the product it describes. The relation is not transitive in the standard, so the answer reports the stated pairs rather than a closure over them. A model needing the chain would have to walk it explicitly, and question 14 does so for the parallel case.

**Query** `tests/queries/cq10_state_dependency.rq`

```sparql
PREFIX vdi3682: <https://w3id.org/aias/odp/vdi3682#>

SELECT ?state ?stateKind ?dependsOn ?dependsOnKind
WHERE {
  ?state vdi3682:dependency ?dependsOn .
  ?state     a ?stateKind     . ?stateKind     rdfs:subClassOf* vdi3682:State .
  ?dependsOn a ?dependsOnKind . ?dependsOnKind rdfs:subClassOf* vdi3682:State .
} ORDER BY ?state ?dependsOn
```

**Results**

| Case | state | stateKind | dependsOn | dependsOnKind |
|---|---|---|---|---|
| tc1_decomposition | *(empty)* |  |  |  |
| tc2_parallel | P2a | Product | P2b | Product |
| tc2_parallel | P2b | Product | P2a | Product |
| tc3_alternative | *(empty)* |  |  |  |

**Interpretation.** The dependency of Part 1, 4.1.2, which the standard carries alongside the flow.
Only case 2 answers, with two rows: `P2a` and `P2b` depend on each other.

That is what holds a parallel run together. The two products arise from
branches running alongside each other, and the dependency states that they

parallelism and therefore no dependency, which is the correct empty answer.

The relation is symmetric in these models and the pattern does not assert it as
such, so both directions appear as stated.

### CQ 13: Which flows are simple, which parallel, and which alternative?

The distinction the three test cases are built around. Part 1, 4.2.1 models a parallel run as a partially shared flow and Figure 8 models an alternative as a product arising from one path or the other, and both are subclasses of the plain flow. Anchored on the flow rather than on one of the two subclasses, so a simple flow appears as well. A model that states no parallelism answers with simple flows only, which is the correct answer rather than an empty one. The direct class is reported: the reasoner materialises ParallelFlow, and reporting Flow alongside it would say nothing.

### CQ 26: Which resources and operators are named but described no further?

Part 1, 4.4 gives an element two ways to say more about itself: the identification names it, the characteristic states a property of it. An element carrying an identification and nothing else has a name and no content. Narrower than question 24 on purpose, and asking something else. That question finds what was never named. This one finds what was named and then left at that, which is the state a description reaches halfway through and should not stay in. Restricted to operators and resources, the two kinds a reader asks about: an operator states what happens and a resource states what does it, and neither is answerable from a label alone. A state is often fully described by its kind and its name, so including it would report ordinary modelling as a gap.

**Query** `tests/queries/cq26_sparse_elements.rq`

```sparql
PREFIX vdi3682: <https://w3id.org/aias/odp/vdi3682#>
PREFIX rdfs:    <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?element ?elementKind ?shortName
WHERE {
  VALUES ?root { vdi3682:ProcessOperator vdi3682:TechnicalResource }
  ?element a ?elementKind . ?elementKind rdfs:subClassOf* ?root .
  ?element vdi3682:isIdentifiedBy ?id .
  OPTIONAL { ?id vdi3682:shortName ?shortName }
  FILTER NOT EXISTS { ?element vdi3682:isCharacterizedBy ?anyCh }
  FILTER NOT EXISTS { ?element a ?narrower . ?narrower rdfs:subClassOf+ ?elementKind }
} ORDER BY ?elementKind ?element
```

**Results**

| Case | element | elementKind | shortName |
|---|---|---|---|
| tc1_decomposition | O1 | ProcessOperator | O1 |
| tc2_parallel | *(empty)* |  |  |
| tc3_alternative | *(empty)* |  |  |

**Interpretation.** Elements carrying a name and nothing else. One row in case 1, `O1`, and none in
the others.

Narrower than question 24 and asking something else. That question finds what
was never named, this one finds what was named and then left at that, which is
the state a description passes through halfway and should not stay in.

Restricted to operators and resources, since those are the two kinds a reader
asks about. A state is often fully described by its kind and its name, so
