## Further questions

### CQ 01: Which controls exist, and of which kind is each?

351-43-22 defines automating as implementing self-acting functions. The kind of control is the manner in which a control runs, which is why the control types are subclasses of control rather than a separate attribute. The most specific asserted type is reported, not every inferred superclass. Reporting the whole chain up to Control would only repeat what the class hierarchy already states. The pattern class is reached over the subclass hierarchy rather than by asking for it as a type. The reasoner materialises the direct type of an individual, so a query anchored on the general class alone returns nothing.

**Query** `tests/queries/cq01_controls_and_kind.rq`

```sparql
PREFIX iec60050:  <https://w3id.org/aias/odp/iec60050#>
PREFIX inst: <https://w3id.org/aias/odp/iec60050/instances#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX owl:  <http://www.w3.org/2002/07/owl#>
SELECT ?control ?kind
WHERE {
  ?control a ?kind .
  ?kind rdfs:subClassOf* iec60050:Control .
  FILTER NOT EXISTS {
    ?control a ?narrower .
    ?narrower rdfs:subClassOf+ ?kind .
    ?narrower rdfs:subClassOf* iec60050:Control .
  }
} ORDER BY ?control ?kind
```

**Results**

| Case | control | kind |
|---|---|---|
| tc1_openloop | ControlA | OpenLoopControl |
| tc2_closedloop | ControlB | SamplingControl |
| tc3_resetcircuit | ControlC | OpenLoopControl |

**Interpretation.** One control per case, each with its direct kind. Case 2 reports a sampling
control rather than a closed-loop control, since the reasoner materialises the
narrowest class and the query reports that one.

### CQ 02: Which controls are open-loop, which closed-loop?

351-47-01 and 351-47-02. The two are deliberately not disjoint, since 351-47-02 admits open-loop control inside a closed action path. An control may therefore fall under both, and the query reports that rather than forcing a choice between them. The pattern class is reached over the subclass hierarchy rather than by asking for it as a type. The reasoner materialises the direct type of an individual, so a query anchored on the general class alone returns nothing.

**Query** `tests/queries/cq02_open_or_closed_loop.rq`

```sparql
PREFIX iec60050:  <https://w3id.org/aias/odp/iec60050#>
PREFIX inst: <https://w3id.org/aias/odp/iec60050/instances#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX owl:  <http://www.w3.org/2002/07/owl#>
SELECT DISTINCT ?control
       (IF(BOUND(?o), "yes", "no") AS ?openLoop)
       (IF(BOUND(?c), "yes", "no") AS ?closedLoop)

  ?type rdfs:subClassOf* iec60050:Control .
  OPTIONAL { ?control a ?ot . ?ot rdfs:subClassOf* iec60050:OpenLoopControl   . BIND(1 AS ?o) }
  OPTIONAL { ?control a ?ct . ?ct rdfs:subClassOf* iec60050:ClosedLoopControl . BIND(1 AS ?c) }
} ORDER BY ?control
```

**Results**

| Case | control | openLoop | closedLoop |
|---|---|---|---|
| tc1_openloop | ControlA | yes | no |
| tc2_closedloop | ControlB | no | yes |
| tc3_resetcircuit | ControlC | yes | no |

**Interpretation.** The distinction the pattern exists for. Cases 1 and 3 are open-loop, case 2
closed-loop.

That case 3 is open-loop despite its closed path is the whole point of it, and
question 08 is where that becomes readable.

### CQ 03: Which special kinds of control does a case use?

Below the open and closed loop the standard names further kinds: sampling control 351-47-20, cascade control 351-47-25, adaptive, fuzzy, robust, model-based and rule-based control among them. They say how a control works rather than whether its path returns. Asked of the case rather than of the class hierarchy. Listing the kinds the pattern knows would answer the same whichever model is loaded; reporting the ones a case uses says what this control is. The genus is reported alongside, since every special kind sits under the open or the closed loop and the answer is only readable against that: a sampling control is a closed loop that acts at intervals rather than continuously.

**Query** `tests/queries/cq03_special_control_kinds.rq`

```sparql
PREFIX iec60050:  <https://w3id.org/aias/odp/iec60050#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?control ?specialKind ?genus
WHERE {
  ?control a ?specialKind .
  ?specialKind rdfs:subClassOf+ iec60050:Control ; rdfs:subClassOf ?genus .
  FILTER(?specialKind NOT IN (iec60050:OpenLoopControl, iec60050:ClosedLoopControl))
  FILTER(isIRI(?genus))
} ORDER BY ?control ?specialKind
```

**Results**

|---|---|---|---|
| tc1_openloop | *(empty)* |  |  |
| tc2_closedloop | ControlB | SamplingControl | ClosedLoopControl |
| tc3_resetcircuit | *(empty)* |  |  |

**Interpretation.** Only case 2 answers, with one row: its control is a sampling control, which
sits under the closed loop.

Asked of the case rather than of the class hierarchy. The pattern knows seven

### CQ 04: Which reference, manipulated and controlled variable does a control have?

have? The three variables of 351-42 that make a control describable: the reference variable states what is wanted, 351-42-05, the manipulated variable is what the control sets, 351-42-08, and the controlled variable is what it acts on, 351-42-09. Reported in one row per control, with the three collected rather than joined. Listing them as separate rows would repeat the control three times and say nothing more. An open-loop control may state fewer of them, and that is the point of asking all three together: the answer shows which of the three a case has committed to.

**Query** `tests/queries/cq04_control_variables.rq`

```sparql
PREFIX iec60050:  <https://w3id.org/aias/odp/iec60050#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?control ?controlKind
       (GROUP_CONCAT(DISTINCT COALESCE(STR(?reference),   ""); separator=", ") AS ?referenceVariable)
       (GROUP_CONCAT(DISTINCT COALESCE(STR(?manipulated), ""); separator=", ") AS ?manipulatedVariable)
       (GROUP_CONCAT(DISTINCT COALESCE(STR(?controlled),  ""); separator=", ") AS ?controlledVariable)
WHERE {
  ?control a ?controlKind . ?controlKind rdfs:subClassOf* iec60050:Control .
  FILTER NOT EXISTS { ?control a ?narrower .
                      ?narrower rdfs:subClassOf+ ?controlKind ;
                                rdfs:subClassOf* iec60050:Control }
  OPTIONAL { ?control iec60050:hasReferenceVariable   ?reference }
  OPTIONAL { ?control iec60050:hasManipulatedVariable ?manipulated }
  OPTIONAL { ?control iec60050:hasControlledVariable  ?controlled }
} GROUP BY ?control ?controlKind ORDER BY ?control
```

**Results**

| Case | control | controlKind | referenceVariable | manipulatedVariable | controlledVariable |
|---|---|---|---|---|---|
| tc1_openloop | ControlA | OpenLoopControl |  | y |  |
| tc2_closedloop | ControlB | SamplingControl | w | y | x |
| tc3_resetcircuit | ControlC | OpenLoopControl |  | y |  |

**Interpretation.** The three variables of a control in one row. Case 2 states all three, cases 1
and 3 fewer.

Collecting them rather than listing them separately is deliberate: three rows
per control would repeat the control and say nothing more.

### CQ 05: Which controls state no controlled variable?

Entry 351-42-09 defines the controlled variable as the variable of the controlled system that the control acts on. A control without one acts on nothing a model can name, so nothing can be said about what it achieves. Legitimate while a description is being sketched and questionable once it is finished. A sequential control, 351-47-04, is the case worth allowing for: it runs through steps rather than holding a variable, and a model of one may well name none. The kind is reported alongside so the two can be told apart. OWL cannot require the variable under the open world assumption, so this reports rather than enforces.

**Interpretation.** Cases 1 and 3 answer, case 2 does not. An open-loop control acting through a

### CQ 08: Where do the kind of action and the kind of path differ?

The case the standard warns about. Entry 351-47-06 defines the reset circuit as a switching system with a closed action path containing at least one binary storage element, and its note states that it has an open action despite the closed path. A model reading a closed path as a closed loop would type it wrongly, and test case 3 is built to be exactly that trap. The three kinds are reported side by side so the divergence is visible rather than inferred: the path is closed, the action is open, and the control is an open-loop control. Cases 1 and 2 agree in all three and answer empty. That the question returns nothing there is what makes the one row of case 3 mean something.

### CQ 09: Which action lines make up a path, and which variable does each carry?

351-44-03 defines the action path as a directed path connecting two variable quantities, and 351-44-04 the action line as a part of it between two functional units. Together they resolve a path into the chain of Figures 1 and 2 of the standard. Without the chain a path can only be asserted to be open or closed. With it the assertion becomes checkable against the units and variables a model actually records, which is what question 10 does.

### CQ 10: Does the chain of a path close into a cycle?

The question that separates test case 2 from test case 3. A chain closes when a functional unit can be reached from itself by following action lines of the same path, that is when the chain contains a cycle. That is the returning path of 351-47-03. The test is reachability, not adjacency. In any chain the end of one line is the start of the next, so adjacency alone would report every path as closing. A cycle requires a unit to lie both before and after itself. All three cases are reported, closing or not, together with the kind of action and the kind of control, so the answer shows the combination: case 1: chain does not close, open action,   open-loop control case 2: chain closes,         closed action, closed-loop control case 3: chain closes,         open action,   open-loop control Cases 2 and 3 have the same structural answer and differ in the action alone. That is what 351-47-01 turns on: the closed action, not the closed path. The query reports a mismatch, it does not forbid one. OWL cannot require a closed action path to contain a cycle, so a model may assert a closed path over an open chain. Catching that is a task for SHACL.

**Query** `tests/queries/cq10_chain_closes.rq`

```sparql
PREFIX iec60050:  <https://w3id.org/aias/odp/iec60050#>
PREFIX inst: <https://w3id.org/aias/odp/iec60050/instances#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX owl:  <http://www.w3.org/2002/07/owl#>
SELECT ?control ?pathKind
       (IF(COUNT(?cyclicUnit) > 0, "yes", "no") AS ?chainCloses)
       ?actionKind ?controlKind
WHERE {
  ?control iec60050:runsOverActionPath ?path ; iec60050:hasAction ?action .
  ?path   a ?pathKind   . FILTER(?pathKind   IN (iec60050:OpenActionPath, iec60050:ClosedActionPath))
  ?action a ?actionKind . FILTER(?actionKind IN (iec60050:OpenAction,     iec60050:ClosedAction))
  ?control a ?controlKind .
  FILTER(?controlKind IN (iec60050:OpenLoopControl, iec60050:ClosedLoopControl))
  OPTIONAL {
    # A unit reachable from itself along the lines of this path.
    ?path iec60050:hasActionLine ?anyLine .
    ?anyLine iec60050:fromUnit ?cyclicUnit .
    ?cyclicUnit (^iec60050:fromUnit/iec60050:toUnit)+ ?cyclicUnit .
  }
} GROUP BY ?control ?pathKind ?actionKind ?controlKind
ORDER BY ?control
```

**Results**

| Case | control | pathKind | chainCloses | actionKind | controlKind |
|---|---|---|---|---|---|
| tc1_openloop | ControlA | OpenActionPath | no | OpenAction | OpenLoopControl |
| tc2_closedloop | ControlB | ClosedActionPath | yes | ClosedAction | ClosedLoopControl |
| tc3_resetcircuit | ControlC | ClosedActionPath | yes | OpenAction | OpenLoopControl |

**Interpretation.** Whether the chain returns to where it started, computed over the transitive
closure of the lines rather than by looking for adjacency.

The distinction matters. An earlier version of this question tested whether two
lines met, and every chain came out as closing. Following the path to see
whether a unit is reachable from itself is what actually answers it.

Case 1 answers no, cases 2 and 3 yes. Case 3 answering yes alongside an open
action and an open-loop control is the reset circuit again, seen from the chain
rather than from the type.

### CQ 11: Which branches does a control loop have?

351-47-07 defines the forward path from the output of the comparing element to the output of the controlled system, 351-47-08 the feedback path from an output of the controlled system back to the comparing element. Only a control loop has both, so the answer is empty for a control chain, which is the expected result on test cases 1 and 3.

### CQ 12: Which action lines belong to no action path?

Entry 351-44-04 has an action path composed of action lines. A line outside every path connects two functional units without taking part in the chain a control runs over, so nothing reaches it and it reaches nothing. The two units are reported alongside, since that is what identifies the line: a line has no name of its own in the standard, it is the connection from one unit to another. Empty on the three cases, which is the intended state.

Clause 351-45 names the time and quality characteristics a control may be described by, and they are supplied as named individuals. A model states a value for as many as it cares about. Listing them would report the same thirteen whatever case is loaded. Holding them against the case reports what this control actually specifies, and the unstated half is the useful one: a control with no stated dead time carries no timing a requirement could be checked against.

**Query** `tests/queries/cq24_characteristics_used.rq`

```sparql
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?characteristic ?kind ?standing ?quantity ?unit
WHERE {
  ?c a ?kind . ?kind rdfs:subClassOf* iec60050:Characteristic .
  FILTER NOT EXISTS { ?c a ?narrower .
                      ?narrower rdfs:subClassOf+ ?kind ;
                                rdfs:subClassOf* iec60050:Characteristic }
  OPTIONAL {
    ?value iec60050:forCharacteristic ?c .
    OPTIONAL { ?value iec60050:quantity ?quantity }
    OPTIONAL { ?value iec60050:unit     ?unit }
  }
  BIND(IF(BOUND(?value), "stated", "not stated") AS ?standing)
  BIND(REPLACE(STR(?c), ".*#", "") AS ?characteristic)
} ORDER BY ?standing ?kind ?characteristic
```

### CQ 25: Which real-time capability is stated, and what is it bound to?

351-54-06. Real time is the capability of a system to keep tasks in a runnable state so that they react within a pre-determined time interval, not a property of time itself. The pattern follows that reading, so the capability is instantiated and the interval stated separately as a characteristic value.

**Query** `tests/queries/cq25_real_time_capability.rq`

```sparql
PREFIX iec60050:  <https://w3id.org/aias/odp/iec60050#>
PREFIX inst: <https://w3id.org/aias/odp/iec60050/instances#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX owl:  <http://www.w3.org/2002/07/owl#>
SELECT ?item ?capability
WHERE {
  ?item iec60050:hasProperty ?capability .
  ?capability a iec60050:RealTimeCapability .
} ORDER BY ?item
```

**Results**

| tc1_openloop | *(empty)* |  |

**Interpretation.** One row, case 2: the programmable controller carries a real-time capability.
Entry 351-45-32 defines it as the capability to meet a required response time.

The capability is reported as a thing rather than as a number, since that is
