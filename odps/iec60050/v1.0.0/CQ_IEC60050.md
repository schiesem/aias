# Competency Questions: IEC 60050-351 Pattern (Control Technology)

Ontology design pattern for the terminology of control technology, above all
for the distinction between open-loop and closed-loop control.

Normative basis: DIN IEC 60050-351:2014, International Electrotechnical
Vocabulary, Part 351: Control technology, identical to IEC 60050-351:2013.

IRI: `https://w3id.org/aias/odp/iec60050/`
Named individuals: `https://w3id.org/aias/odp/iec60050/instances/`

Every question is answered from the A-box of a modelled case. The pattern ships
named individuals for the characteristics of 351-45 and for the control
functions, and a case uses them as it needs them. Those individuals are A-box
themselves, but listing them is not a competency question: the answer would be
the same whichever case is loaded.

One question, 24, holds such a catalogue against a case and reports per entry
whether the case states a value for it. Its query declares that, since the rows
there are the scale rather than the finding.

The catalogue is deliberately short. The pattern takes up 92 of the 409 entries
of the standard, and `REFERENCE.md` records which and why. Questions are asked
where a model has to answer something, not for every term that exists.

The answer column states what a query returns, not how it is computed.

## On questions 08 and 19

These two carry the weight of the pattern.

**Question 08** is the trap the standard warns about. Entry 351-47-06 defines
the reset circuit as a switching system with a closed action path, and the note
to the entry states that it has an open action despite that. A model reading a
closed path as a closed loop would type it wrongly, and test case 3 exists to
be exactly that case. The question reports control kind, action kind and path
kind side by side, so a divergence is visible rather than inferred.

**Question 19** walks the chain from a device to what it does: a physical unit
realises a functional unit, that unit sits on action lines, and the lines make
up a path whose kind says whether the loop returns. None of that is asserted on
the device.

A device may realise several units at once, and the answer reports that rather
than resolving it. Device C of test case 2 realises four, and asking it for one
role would require a cardinality the standard does not state.

The AIAS alignment uses this chain. `aias:Resource` is a subclass of
`iec60050:PhysicalUnit`, so a model that states a sensor or a controller can be
asked the same question across the subdomains.

## Open points for modelling

1. **Open-loop and closed-loop control are not disjoint.** 351-47-02 admits
   open-loop control in a closed action path, so a disjointness axiom would
   contradict the standard. What separates the two is the action, 351-47-04
   against 351-47-06, which the model states explicitly.

2. **The genus of a control type is taken from the standard, never assumed.**
   Most definitions in 351-47 begin with "closed-loop control in which ..." and
   thereby fix the genus. Where they do not, as with programmed control
   (351-47-20) and computer control (351-47-52), the type sits directly under
   control and a model may assign it either way.

3. **`actuator` is not the German Aktor.** 351-49-07 defines the actuator as
   the unit generating the manipulated variable to drive the final controlling
   element, that is the signal side. The element acting on the mass or energy
   flow is the final controlling element, 351-49-08. Both are kept apart here,
   since the common mistranslation would otherwise enter the model.

4. **The final controlling element belongs to the controlled system.**
   351-49-08 states this, whereas VDI 3682 would treat a valve as a technical
   resource executing a process operation. The pattern records the membership
   as a relation rather than a class, so the alignment can hold both readings
   without contradiction.

5. **The standard defines no sensor.** It says sensing element, 351-56-26, and
   grades further to measuring transducer and measuring transmitter, 351-56-28
   and -29, by accuracy and by signal standardisation. The measuring
   transmitter is the natural handover point to the communication pattern,
   since that is where a standardised signal arises.

6. **Real time is a capability, not a duration.** 351-54-06 defines real-time
   capability as keeping tasks runnable so they react within a pre-determined
   time interval. The pattern follows that reading, so a model states the
   capability and the interval separately.

7. **Terms the standard does not define.** Availability, reliability, accuracy,
   resolution and safety integrity have no entry, and neither has cycle time.
   `REFERENCE.md` records where each would have to come from. A model needing
   them has to import another vocabulary rather than invent one here.

8. **Control levels are left out.** 351-55-12 to -15 define three levels,
   individual, group and plant. The graphical notation of this work follows the
   automation pyramid with five levels, so the two do not align, and mixing
   them would create friction rather than structure.
